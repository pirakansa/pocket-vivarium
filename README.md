# Pocket Vivarium — こもれびの村

MEHSを逐一操作せず、性格・欲求・経験から生まれる稼働を見守る箱庭です。記録の生成はGitHub Actions、表示はGitHub Pagesで行います。SitesとlocalStorageは使用しません。

## 起動・検証

Node.js 22を使用します。追加パッケージやビルドは不要です。

```sh
# 旧形式の記録の場合は、一度実行して現実時刻へ移行
node scripts/update-state.cjs
node tests/update-state.cjs
node tests/player.cjs
python3 -m http.server 8000 --directory dist
```

http://localhost:8000 を開きます。

## 現実時間と6時間の記録

JSONは `schemaVersion: 3`、`mode: "realtime"` です。UTCの偶数時を更新基準とし、基準時刻の **過去2時間＋先4時間＝計6時間** を保持します。

| 12時基準の例 | 用途 |
|---|---|
| 10〜12時 | 振り返り |
| 12〜14時 | 現在からの記録 |
| 14〜16時 | 更新遅延への余裕 |

14時基準へ更新する際は、12〜16時の4時間をそのまま引き継ぎ、16〜18時だけ生成します。重複する記録や経験を再計算しません。1回の遅延・失敗なら前回の先行記録を表示できますが、記録の終端を超えたら最後の状態で待機します。

基準がUTC偶数時のため、日本時間では奇数時です。通常の実行は基準から17分後。厳密に「現在から過去2時間＋未来4時間」を毎秒保持するのではなく、2時間ごとに基準が進む窓です。画面の振り返り範囲は閲覧時点の過去2時間です。

- `windowStart`：6時間窓の開始日時（ISO UTC）
- `anchorAt`：その更新の基準日時
- `windowEnd`：6時間窓の終了日時
- `frames`：5分刻みの72時点。各 `at` は絶対日時、`state` は村の状態
- `endState`：終了日時時点の状態。次の生成へ引き継ぐ
- `generatedAt`：生成した実際の日時
- `worldOrigin`：村の通算時刻の起点。`state.hour` はここからの経過時間

旧相対時間形式は初回に自動移行します。以前の終了状態を初回窓の開始に置き、時刻を日本時間の昼夜へ合わせて6時間分を生成します。この過去部分は旧記録の実測履歴ではなく、移行時に作る記録です。一度移行した後は、絶対日時と状態の連続性を維持します。

## 画面

- 起動時から現実の現在時刻に対応した村を表示。時計表示は日本時間。
- スライダーで過去2時間へ戻り、「現在に戻る」でLIVE表示へ復帰。
- 過去表示中の日時は固定され、何分前かを表示。早送り・相対時間再生は廃止。
- 未来の記録は表示操作で選べません。JSON自体は公開データであり、秘匿ではありません。
- 60秒ごと、および画面に戻った時にJSONを再取得します。現在表示中は新しい窓へ自動で切り替わります。
- 振り返り中にその時点が窓から外れた場合も、ブラウザ内でその状態と日時を保持します。再読み込みではLIVEに戻ります。
- 更新失敗時は前の記録を維持して再試行。記録が尽きたら「更新待ち」を表示。
- MEHSの施設間の移動はJSONに保存し、画面は保存済みの経路と時刻から位置を補間します。機体の小さな揺れや旧記録の散策は描画用アニメーションで、JSONを変更しません。

## 自動更新と公開

`.github/workflows/deploy-pages.yml` が、日本時間 **01:17、03:17、…23:17** に1日12回実行します（cron `17 */2 * * *`、UTC）。

1. 最新mainを取得。
2. スケジュール実行、手動で `update_state` を選んだ場合、または旧形式からの移行時に記録を生成。
3. 重複する4時間は保持し、不足部分だけを前回終端から順に計算。
4. テスト成功後、状態・履歴をbotのnoreply名義でコミット。
5. 同じワークフロー内で `dist/` をPagesに公開。

同じ基準時間の再実行では二重に進めません。実行が漏れても、次回に前回終端から計算して追いつきます。1年を超える欠落は自動補完せずエラーとし、手動確認します。通常のmainへのpushは公開のみですが、旧形式が残っていれば初回移行も行います。

手動実行：**Actions → Update village and deploy Pages → Run workflow**。必要に応じて `update_state` を選択します。追加のAPIキーは不要です。mainへのbotの書き込みとPages公開が許可されている必要があります。pushに失敗したら公開も停止し、force pushはしません。

GitHubの定期実行には遅延や実行漏れがあり、2時間の余裕がそれを完全に保証するものではありません。GitHub Pages側の配信キャッシュによる反映の遅れもあり得ます。

## シミュレーション・履歴

充電不足・機体コンディション・通信欲求・好奇心・性格・資源回収経験・共有電力セル・天候・時刻から、充電・休息・資源回収・通信・探索を選びます。昼夜による休息の優先補正は設けず、疲れ具合から休息を選びます。夜も活動を観察できることを重視します。睡眠専用状態・人間関係・天候の自動変化は未実装。生成AIは使用しません。

`data/history/` には前回の窓を直近360本まで保存します。窓が重なるため、各ファイルは独立した2時間区間ではありません。通常更新で約30日相当です。旧形式の履歴も保持対象です。履歴はPages配信対象外ですが、公開リポジトリでは読めます。画面から過去バッチを選択する機能はまだありません。村の手帳は各状態内で直近35件を保持します。

## 管理先

GitHubでソース・記録を管理し、GitHub Pagesへ公開します。公開URLはActionsの `github-pages` Environmentから確認できます。

## 個体ID

MEHSの名前は廃止し、画面・手帳ともに **MEHS #1、MEHS #2…** と表示します。内部の `people[].id` は正の整数で、描画用の座標や選択もこのIDで管理します。人数・並び順が変わっても、同じ個体を識別します。

各状態の `nextResidentId` は次に割り当てるIDです。現在は4から開始し、将来の個体追加ではこの値を使用して増やします。個体がいなくなっても減らさず、過去のIDを再利用しない設計です。組み立て・稼働寿命・世代交代に利用します。

旧ハル→1、旧ユイ→2、旧レン→3として移行します。`scripts/migrate-identities.cjs` が最新JSONと保存済み履歴の名前・手帳を変換し、名前フィールドを削除します。数値や日時、行動の連続性は保持します。Gitの過去コミットには変更前の名前も残ります。

ワークフローは生成前にID移行を実行します。ローカルで古いJSONを使う場合も、最初に次を実行してください。

```sh
node scripts/migrate-identities.cjs
node tests/identities.cjs
```

## MEHSの世界観

人間ではなく、小さな自律ロボット（MEHS）が稼働する箱庭です。アンテナ・表示パネルの目・Mマークを持つアバターで、機体ごとの色とIDで区別します。充電ステーション・電力セル・資源回収・通信・探索・整備として表現します。夜を理由に活動を止めません。

既存記録との互換性のため、内部の数値キーは維持します。`hunger` は充電不足（大きいほど補給が必要）、`energy` は機体コンディション、`food` は共有電力セル、`social` は通信欲求として扱います。`kind: "mehs"` を個体に設定します。移行は表現だけを変更し、数値・日時・ID・行動の順序は引き継ぎます。最新と保存済みの履歴をワークフローで自動移行します。

将来の世代交代は、新しい機体の組み立て・起動、設計や特性の継承、稼働寿命・活動終了として考えます。人間の繁殖ではなく、設備と設計の継承による機体追加・引退を実装しています。

```sh
node scripts/migrate-mehs.cjs
node tests/mehs.cjs
```

## 組み立て・稼働寿命・世代交代

- 初期機体の稼働開始は、この機能導入時の6時間窓の先頭です。過去の機体を突然引退させません。新しく起動する機体は、実際の村の起動時刻を保持します。
- 各機体の稼働寿命はIDから決まる **21〜35日**。同じIDなら再計算しても同じ寿命です。経年耐久は稼働年齢・雨天・長引く充電不足の追加摩耗から低下し、充電・整備では若返りません。
- `energy`（機体コンディション）と `durability`（経年耐久）は別です。充電量0で即引退はせず、長引く充電不足は累積摩耗を少し増やし、整備はコンディションを回復します。劣化した機体は画面上の移動もゆっくりになります。
- 資源回収で電力セルと少量の部品を集めます。保管上限は電力セル72、部品64。稼働中の機体数に応じて常時電力を消費します。
- 資源に余裕があり、前の組み立て後の待機時間も終わっていると、好奇心・冒険性・仲間への関心から組み立て担当を選びます。充電不足や機体状態が悪い機体は担当しません。
- 機体数nに対し部品 `12+4n` と電力セル6を消費。消費後もセル `12+6n` を確保できることが必要です。機体数が増えると負担が増すため、無制限には増えません。途中キャンセルはありません。
- 組み立ては **4時間**。1件ずつ進め、完了から **12時間** は新しい組み立てを始めません。初期導入後は6時間待ってから判定します。
- 組み立て開始時にIDを予約し、`nextResidentId` を増やします。担当は従来の体調・在庫・工房滞在条件を満たす機体から等確率で選びます。協力機体は他の稼働機から、性格3傾向の差の絶対値の合計に1を足した重みで抽選します。色や目の形も主担当からの継承を基本とし、ときどき変異します。経験回数は新機体で0からです。
- `parentIds` に設計元、`generation` に世代を記録。`lineage` は機体が引退しても残る設計・起動・引退の台帳です。実際の血縁ではありません。
- 引退時は稼働機体一覧から外し、設計と経験を台帳に保存。回収部品8個を共有在庫へ残します。IDは再利用しません。
- 全機が引退したら、継承設備が専用の復旧用備蓄を使い、最後の設計から4時間かけて次の機体を起動します。組み立て担当が途中で引退した場合も設備が引き継ぎます。永久停止を避けるための明示的な救済ルールです。
- 組み立て・引退・起動は5分刻みで記録され、通常の6時間窓と過去2時間の振り返りに反映されます。すでに生成済みの行動を再計算せず、新規生成部分から進みます。

画面では稼働機体数・部品・組み立て進捗・起動予定・世代・設計元・経年耐久・直近の引退機体を確認できます。家系図のグラフ表示、手動組み立て、部品ごとの性能は未実装です。

```sh
node scripts/migrate-lifecycle.cjs
node tests/lifecycle.cjs
```

保存済みの古い履歴は当時のまま保持し、最新6時間窓にだけ初期メタデータを補います。世代台帳は最新状態から次回へ引き継ぐため、30日間のJSON履歴保持とは別に存続します。台帳は世代数に応じて増えます。

## ランダムな発見と個体差

世界の抽選には保存された `rngState`（xorshift32）を使用します。`Math.random()` や実行日時をシミュレーションに使わず、同じ終了状態からなら同じ結果を再現します。初期シードは固定で、抽選するたびに進んだ値を状態JSONへ保存します。既存の4時間の重複区間は抽選し直しません。寿命は従来どおりID由来の21〜35日で、突然の故障・ランダムな引退は追加していません。

### 行動の抽選

最高の優先度との差が8点以内で、実行可能な行動だけを抽選します。点数が高いほど選ばれやすく、性格による優先度は維持します。充電不足85以上で在庫がある場合は充電、コンディション15以下なら整備を優先し、切迫した状態を抽選で無視しません。

### 発見と通信

回収・探索の行動を新たに選んだ時、4%で「光学モジュール」を発見します。探索ではさらに14%の範囲で、未発見の場所（電力セルの集積地・古い通信中継器・旧工房の記録）を発見します。同じ機体は発見成功後4時間、追加の発見を行いません。

- 光学モジュールは部品在庫を2増やし、特別な部品として最大12個まで保存。次の組み立てで1個使い、継承元と異なる目の形を確実に採用します。
- 電力セルの集積地を発見すると、その後の回収で25%の確率でセルを1個追加します。その他の場所は、行動の手がかりとして機能します。
- 発見情報を知る機体は、通信時に同じ場所にいる、まだ知らない別の機体へ共有します。受信機体は6時間、関連する回収・探索の優先度が10点上がり、対応行動を行うと手がかりを消費します。
- 直近32件を `finds`、発見済みの場所を `sites`、各機体の知識を `knowledge` に保存。画面は直近4件の発見と、発見した場所・特別な部品の数を表示します。
- 特別な部品は発見ID・発見機体・時刻とともに保存。組み立てと起動機体、設計台帳の `inspiration` にも引き継ぎ、「誰の発見が次の機体につながったか」を追えます。

### 新機体の小さな変異

性格の各傾向は設計元のどちらかを等確率で選んで継承します。それぞれ90%で±0.15、10%で±0.75の一様な変異を加え、0.5〜3.5に収めます。経験回数は性格へ直接変換しません。通常の目は55%で主担当の形を継承し、45%で同じ形を含む3種類から抽選します。光学モジュールを使う場合は必ず別の形になります。ボディ色は55%で主担当の色を継承し、45%で同じ色も含む6色のカラーパレットから抽選します。目は角型・丸型・横長バイザーの3種類。抽選した設計を組み立て開始時点で保存するため、起動時や再実行で再抽選しません。経験の回数は0からです。

画面には仕様名・継承した発見部品・短時間のイベントマークを表示します。発見後30分間、関係する機体に✦が付きます。既存機体・生成済みの記録は維持し、新規生成する部分から発見と変異が発生します。

```sh
node tests/random.cjs
```

乱数の再現性、近い優先度だけの抽選、切迫時の充電、発見・共有・部品継承、一括計算と分割計算の一致を確認します。大規模な事故や突然の故障は追加していません。

## 雨と累積摩耗

天候は保存済み乱数から2時間ごとに抽選します。その区間が雨になる確率は25%で、晴れ・雨が続く場合もあります。発生時刻は村の時刻で管理し、スケジュール遅延・再実行・まとめての計算でも同じ天候になります。切り替わりは稼働ログに記録します。

- 通常の5分は5分相当の摩耗。
- **雨の中で移動・資源回収・探索していた5分だけ、7.5分相当（1.5倍）の摩耗**。
- 充電・整備・組み立て中や屋内では、雨の追加摩耗はありません。広場での通信も今回の追加対象外です。
- 計算対象は直前の5分間の移動・行動と天候です。次の行動を選んだ瞬間に過去の雨曝露を付け替えません。
- `activatedHour` からの実年齢と、`rainWearHours`（雨による追加の摩耗時間）を分けて保存。`wearHours` は実年齢・雨・充電不足による摩耗の合計で、これが21〜35日相当の機体固有の限界に達すると引退します。寿命の抽選や突然の故障はありません。
- 屋内の充電・整備はコンディションを回復しますが、累積摩耗は戻しません。引退時の台帳にも摩耗と雨の追加分を残します。
- 既存機体は過去の追加摩耗を0として移行し、年齢から通常摩耗を引き継ぎます。生成済みの過去・未来の行動を再計算せず、新しく生成する部分から天候と追加摩耗が発生します。

雨で回収・探索の優先度が下がる既存の判断も維持します。実際の寿命短縮は雨の割合と屋外活動量によって変わり、常に1.5倍速で老化するわけではありません。表示には累積摩耗と雨による追加分を追加しています。

```sh
node tests/weather.cjs
```

## 観察を主役にしたGUI

村の大きな箱庭画面を中心に、ポートレート付きの機体一覧と「機体・工房・できごと」の観察ノートを配置しています。機体を選ぶとポートレート、行動、ひとこと、充電量・コンディション・通信欲求が見えます。設計・摩耗・優先度は折りたたみで確認できます。

機体数・電力セル・部品は地図上のHUDに表示。工房タブで組み立て進捗、できごとタブで発見と稼働ログを確認できます。過去2時間のスライダーは「時間をさかのぼる」を開いて操作します。画面幅が狭い端末ではノートを地図の下へ配置します。

背景の工房・林・噴水・望遠鏡・水辺、機体のポートレートはHTML/SVG/Canvasで描画します。外部画像や新しいパッケージには依存しません。今回の変更は表示側のみで、状態生成・天候・寿命・定期実行のルールは変更しません。

## 自作ルーチンと日替わりの外界

MEHSは経験が8回に達すると小さなルーチンを組み、実際に実行して行動判断へ使い、通信で仲間へ共有します。現段階の作成は経験に応じたテンプレート合成です。機体ノートで作者、コード、実行・採用回数を確認できます。

外界のJavaScriptはChatGPTの日替わりタスクが[現在版Issue](https://github.com/pirakansa/pocket-vivarium/issues/1)を上書きし、既存の2時間ごとのActionsが読みます。外界のソースはGit・状態JSON・Pagesに保存せず、runnerの一時領域で使い捨てます。GitHub側の編集履歴は残る場合があります。

出来事は1日1回まで。補給、軽い通信障害、訪問・旅立ち、物語、何も起きない日を扱えます。本体が効果量・採番を管理し、プラグインに翌日への処理予約は許可しません。結果が残っても、イベント固有の処理が積み上がることはありません。生成済み4時間の変更はしないため、交換後すぐに表示へ反映されるとは限りません。

構文・効果の上限・使い捨ての範囲は [プログラム仕様](docs/programs.md) を参照してください。追加依存パッケージ・APIキーは不要です。

```sh
node tests/programs.cjs
```


### 日替わりの変化に対するテスト

外界の自由文はそのまま保存し、用語移行の繰り返しで確定済み履歴を書き換えません。イベントは反映後の状態の日本時間の日付に合わせ、成功・一部成功・見送りを区別し、許可した項目と実際の増減だけを保存します。

`node tests/event-contract.cjs` で人口0・1・上限、組み立て中、日付境界、不正コード・取得失敗、コード交換、30日間の状態変化を確認します。テスト用の村を使い、実際の村の人数や経験値を固定値と比較しません。生成された公開JSONの検証は引き続き行います。詳細は [プログラム仕様](docs/programs.md) を参照してください。

### AIによるMEHSのルーチン改良

経験からのテンプレート自作を残し、既存の日替わり外界タスクが最大3機分のコードと作成理由を一緒に生成します。外界イベントと同じIssueのroutines配列で受け渡します。機体ごとに検査し、合格した現在版1本を実行・共有します。現在版が生成時から変わっていた場合や対象が引退していた場合、不正な候補は既存コードを維持します。新規生成区間だけに反映し、過去や確定済み未来を書き換えません。

機体ノートにはテンプレート由来・AI改良の区別と工夫の理由を表示します。AIのコードも現段階では行動の優先度を提案する範囲で、切迫時の充電・整備は本体が優先します。ActionsからAIのAPIは呼びません。詳細と日替わりタスクの手順は [プログラム仕様](docs/programs.md)、検証は `node tests/ai-routines.cjs` です。


## 長引く充電不足による穏やかな摩耗

- 表示上の充電量が **10以下**（内部の `hunger` が90以上）の状態が連続した時間を `powerShortageHours` に記録します。
- 最初の **2時間は追加摩耗なし**。それを超えた時間に限り、1時間あたり **0.25時間相当**の追加摩耗を `powerWearHours` に蓄積します。雨の影響がなければ合計1.25倍です。例えば3時間連続の不足なら追加は15分相当です。
- 充電量が10を超えると連続時間をリセットし、追加摩耗は止まります。蓄積済みの摩耗は充電・整備では戻りません。
- 判定は直前の5分間の充電状態に基づきます。充電の優先ルールは維持し、充電量0で即引退はしません。雨の追加摩耗とは加算し、累積摩耗が既存の寿命限界へ達した場合に通常の引退・継承処理を行います。引退台帳にも充電不足による摩耗を記録します。
- 旧状態で未設定の追加摩耗・連続時間は0として扱い、既存の過去・確定済み未来には補いません。新規生成区間からのみ蓄積します。画面の累積摩耗と経年耐久に反映されます。

`node tests/power-wear.cjs` で猶予時間、回復時の停止・リセット、雨との加算、充電優先、通常の引退、旧記録の保持と分割生成の一致を確認します。


## 独立したヒストリーページ

`history.html` は村の画面とは独立した観察ページです。`dist/index.html` と状態生成のルールは変更せず、稼働個体数・電力セル・部品のグラフを同じ時間軸で表示します。1日・7日・30日を切り替え、タップまたは矢印キーで数値と直前5分間の起動・引退を確認できます。同時刻の起動・引退は、個体数が変わらなくても個別に表示します。

公開ワークフローは状態の保存後に `node scripts/build-history.cjs` を実行し、`data/history/` と `dist/state.json` から軽量な `dist/history.json` を生成してPagesへ配信します。生成物はGitへ蓄積せず、履歴原本もPagesへ追加しません。村のページからはこのデータを読み込みません。

- 30日前以降かつ実行時点までの確定した5分刻みの状態を収集し、未来は除外します。表示側でも現在時刻以降を除外します。
- 重複日時は新しい窓を優先し、最新状態を最後に反映します。値を合計したり、欠けた日時を補間したりしません。欠測区間は線を切ります。
- 旧相対時間形式は対象外です。部品数が未記録の古い状態は部品のみ欠測扱いとし、0を捏造しません。起動・引退は各状態の世代台帳の日時から重複を除いて抽出します。
- 最初から30日分を作り直すことはせず、蓄積済みの範囲を表示します。電力セル・部品は小数を含む記録値を使用し、表示は必要に応じ小数第1位に丸めます。
- 履歴ページは60秒ごとに再取得します。エラー時は表示済みのデータを維持します。公開用JSONの更新は従来の定期実行・push・手動公開のタイミングです。

ローカル確認：`node scripts/build-history.cjs` の後、通常のHTTPサーバーで `/history.html` を開きます。`node tests/history.cjs` で重複・未来・保持範囲・欠測・同時刻の起動と引退・原本不変を検証します。


## 現在地・移動・到着

充電の工房（home）、資源の林（forest）、語らいの広場（square）、見晴らしの丘（hill）が実際の行動場所です。移動中は回収・探索・充電・通信の効果や経験を得ず、到着後に実行します。施設容量や待ち行列、遠隔通信、村の拡張は今回追加しません。

- `people[].position` は地図上の論理座標 `x/y` と滞在場所 `area`。移動中のareaはnullです。`journey` に出発座標、目的地と到着座標、出発・到着の村時刻、到着後の行動を保存します。
- 地図座標は `dist/geography.js` で生成側・表示側が共通に使用します。移動は直線で、距離から5分単位に切り上げます。通常速度は毎時1200座標単位。経年耐久によって100〜45%へ低下し、所要時間は出発時に確定します。初期の工房〜林は通常30分です。追加の移動電力ペナルティは設けず、移動中も通常の充電量・コンディションの減少は進みます。
- 移動中もプログラムを判断に使用でき、別の行動を提案すると現在位置から行き先を見直します。切迫した充電（在庫あり）・整備はプログラムより優先して工房へ戻ります。到着時にも切迫状態・在庫を確認し、移動中に在庫がなくなれば充電せず待機します。
- 雨の移動中は屋外として1.5倍の摩耗です。工房へ到着した後は屋内扱い。雨の終了や到着時点から過去の曝露を付け替えません。長引く充電不足の追加摩耗とは加算します。
- 通信による情報・プログラム共有は、同じ場所に滞在している機体だけが対象です。移動中の機体には届きません。近くに仲間がいれば現在の場所で通信でき、いなければ広場へ向かいます。相手がいない通信では通信欲求の解消・通信経験は増えません。すべての到着位置を更新してから行動を処理します。
- 組み立て担当は、これまでの体調・資源条件に加え、工房にいる機体から選びます。移動中・遠方から組み立ては開始しません。起動機体は工房、来訪機は広場から通常の行動を始めます。
- 旧JSONを遡って位置データで埋めません。新規計算の最初に、直前のactivityAreaまたは行動から滞在場所を引き継ぎます。確定済み4時間のJSONと過去履歴はそのまま保持し、旧描画も利用できます。
- 画面の施設間移動は記録の時刻に従って補間します。過去へ戻しても描画だけで旅程が進むことはありません。選択機体の移動先・到着までの目安と、目的地への点線を表示します。画面を開いていなくてもActions側で進行します。

機体用ctxと日替わり生成用コンテキストに現在地・目的地・移動状態・場所ごとの所要時間・同じ場所の仲間数を追加します。詳しくは `docs/programs.md` を参照。`node tests/movement.cjs` で効果の遅延、緊急帰還、雨と退避、行き先の変更、在庫変化、局所通信・共有、同時到着、工房での組み立て、分割計算と記録維持を確認します。

### 性格を示すアンテナ

MAP・機体一覧・詳細画面のアンテナランプは、性格の最大傾向に合わせて通信好き＝緑、備え重視＝黄、探索好き＝青で表示します。同値の優先順は性格名と同じ探索→通信→備えです。現在の数値から描画し、状態JSONは変更しません。
